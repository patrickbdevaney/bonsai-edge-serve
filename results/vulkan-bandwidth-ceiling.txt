Why Vulkan decode is half of CUDA: load width, not bandwidth
============================================================

The Vulkan backend now matches CUDA end to end (15.74 vs 16.77 tok/s
ternary, 19.57 vs 19.03 1-bit) but every Vulkan GEMV we have ever measured
sits at 100-130 GB/s while the CUDA GEMV reaches 241 GB/s at the identical
shape. This file establishes why, and how much is actually available.

WHAT THE DECODE PROFILE SAYS
-----------------------------
`GGML_VK_PERF_LOGGER=1` over a real 32-token generation, median per-shape:

  m        k       MiB     us      GB/s
  248320   5120    303.1   2613.3  121.6     <- output head
  5120     17408    21.2    183.7  121.3
  17408    5120     21.2    193.3  115.3
  12288    5120     15.0    137.6  114.3
  10240    5120     12.5    115.2  113.8
  5120     6144      7.5     81.3   96.7
  6144     5120      7.5     83.9   93.8
  1024     5120      1.2     18.7   69.9
  48       5120      0.1      6.4    9.7

Every real Bonsai shape lands at 93-122 GB/s. The GPU is close to fully
occupied while this happens -- one flush of the perf logger corresponds to
one token, ~67 ms of op time against ~64-71 ms of wall clock -- so decode is
NOT dispatch-bound. Confirming that separately: disabling ggml's fusion
(which increases the dispatch count) costs only 1.0%, and disabling
multi-add costs nothing:

  default      15.68 / 15.70 tok/s
  no-fusion    15.53 / 15.55
  no-multiadd  15.71 / 15.71
  no-both      15.55 / 15.56

So the kernels themselves are the limit, at roughly half of what the
hardware can read.

THE CONTROL THAT WAS MISSING
-----------------------------
A GEMV cannot distinguish "kernel leaves 2x on the table" from "Vulkan
cannot go faster here", because it also does arithmetic. So:
`kernels/vulkan/bandwidth.comp` does nothing but read -- one add per loaded
word, no unpacking, no dot product.

  access pattern                        GB/s
  scalar uint, lane-strided             180.0
  uvec4 (128-bit)                       246 - 250
  4 consecutive uints per lane          241 - 245

  for reference, CUDA on this device:   244.7 (float4 streaming read)

**Vulkan reaches the same ~245-250 GB/s as CUDA -- but only with wide or
per-lane-consecutive loads.** The lane-strided 32-bit pattern, which is what
every GEMV here uses, caps at 180.

Two things this rules out, both worth recording because both were plausible:

* **Memory type is irrelevant.** Thor is unified, and the obvious suspicion
  was that a HOST_COHERENT mapping is uncached and slow to read. It is not:
  DEVICE_LOCAL, DEVICE_LOCAL|HOST_VISIBLE and HOST_VISIBLE|HOST_COHERENT all
  give 180.0 scalar and ~246 wide, identical to three significant figures.

* **The apparent memory-type effect was an ordering artifact.** The first
  case measured in each process reads ~147 GB/s instead of 180, even after
  four warm-up dispatches. Reversing the case order (`BONSAI_BW_REVERSE=1`)
  moves the low number to whichever case now runs first. Had the table been
  read as-printed it would have "shown" that HOST_COHERENT is 25% slower
  than DEVICE_LOCAL, which is false. One reversed run costs nothing and
  settles it.

WIDE LOADS DO WIN -- THE FIRST TEST WAS AT THE WRONG SHAPE (CORRECTION)
-----------------------------------------------------------------------
First attempt: restructure the GEMV so each lane reads four consecutive
words. Measured at K=5120 N=17408 it was SLOWER -- 130.3 GB/s baseline vs
105.0 interleaved and 110.2 grouped -- and this file originally recorded
that as "the hypothesis did not survive."

**That measurement was worthless.** Those weights are 21.2 MiB and Thor's L2
is 32 MB, so the benchmark was L2-resident, not streaming. Worse, the cases
share buffers, so whichever case ran second read weights the first case had
just pulled into L2: the same "q2 int-dot" case swung between 75.7 and 203.0
GB/s across runs purely on ordering. This repo already documented that trap
(K2c, results/gemv-cuda-shapes.txt) and it was walked into anyway.

Re-measured at genuinely streaming footprints, WIDE4 wins, and the variable
is K -- not the footprint:

  K       N        MiB    baseline   WIDE4     delta
  5120    65536     80     120.9     113.2     -6%
  5120   131072    160     116.9     115.4     -1%
  8192    65536    128     113.6     138.3    +22%
  8192   131072    256     115.4     140.1    +21%
  17408   32768    136      90.8     130.1    +43%
  17408   65536    272      89.7     133.5    +49%

All validate against the CPU reference (1.6e-06 to 4.8e-06).

The threshold is words-per-row: `nw = K/16`, and the loop advances by
LANES*4 = 128 words. At K=5120, nw=320, so each lane runs 2.5 iterations and
the ragged tail plus loop overhead swamp the wider loads. At K=17408,
nw=1088 gives 8.5 iterations and the merge pays.

So this is the same shape-adaptive conclusion as W12, in a new place:
**wide loads for large K, lane-strided for small K.**

What it is worth on Bonsai specifically is partial. The real decode shapes
are mostly K=5120 (the output head m=248320, and m=17408/12288/10240/6144),
where WIDE4 does nothing; the K=17408 FFN-down projection is the one that
gains, and it is also currently the slowest ggml shape at 89.7-90.8 GB/s in
our harness. A shape-adaptive kernel captures that piece and not the rest.

SHIPPED: THE 32-QUANT CLASS CAPTURES MOST OF IT
------------------------------------------------
Four consecutive words is the best access pattern but spans two q8_1 blocks,
and ggml's mmvq framework carries one b-scale per call -- so it cannot be
had without changing the contract for every other quant type. Two words can:

  one 32-bit word per lane, lane-strided   180.6 GB/s
  TWO consecutive words per lane           227.9 GB/s   <- fits the framework
  four consecutive / uvec4                 241-249 GB/s

So q1_0 and q2_0 were moved from the 16-quant class to the 32-quant class
(the one IQ1_S/IQ1_M already use). At 32 quants per call, Q2_0 loads two
consecutive uint32 and Q1_0 loads one -- against one and a half words
respectively in the 16-quant class.

End to end, decode tok/s:

  model     MMVQ off   16-quant class   32-quant class   vs baseline
  Q2_0        11.63        15.76            16.75          +44.0%
  Q1_0        15.51        19.03            20.27          +30.7%

Numerically gated at 28 OK / 0 FAIL for both types against the CPU
reference, and generation output is correct.

For scale, the CUDA backend on this box measures 16.77 (ternary) and 19.03
(1-bit). **Vulkan now ties CUDA on ternary and beats it on 1-bit.**

WHERE THIS LEAVES THE NUMBERS
------------------------------
  Vulkan ceiling, wide loads          ~245 GB/s
  Vulkan ceiling, lane-strided scalar  180 GB/s
  our Vulkan GEMV (best)               130 GB/s   72% of scalar ceiling
  ggml Vulkan MMVQ, real shapes      93-122 GB/s  52-68% of scalar ceiling

There is **+38% available without changing the access pattern at all** --
just closing the gap to the lane-strided ceiling -- and **+88% if the wide
path can be made to work**. That is the largest single lever left on this
backend, and it is now a well-posed problem rather than a suspicion.

Contrast with CUDA, where v6's explicit `uint4` loads bought nothing because
the hardware already coalesced the lane-strided form (WIKI K2). **That rule
does not port to Vulkan**: here the two patterns differ by 36%. A design
rule derived on one backend is a hypothesis on another.
