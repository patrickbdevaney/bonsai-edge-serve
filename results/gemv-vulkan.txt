GGUF-ORDER EXTRACTION: GATED AND FASTER
---------------------------------------
The repacked (bit-plane interleaved) layout is not available to
ggml-vulkan -- it receives weights in GGUF order and has no opportunity
to repack. So the extraction ggml would have to use was implemented here
and gated against the same CPU reference.

  q2 int-dot           (repacked)     101.7 / 104.3 / 102.6 GB/s
  q2 int-dot GGUF-ord  (as ggml gets) 106.9 / 106.1 / 110.4 GB/s

Correctness: max rel err 4.783e-06, IDENTICAL to the repacked path. That
is the check that matters, because the wrong extraction (Q2_K's
`(w >> s) & 0x03030303`) also compiles and produces plausible numbers --
it selects the same bit-field from each of four bytes, i.e. weights
strided by 4, silently paired with the wrong activations.

The correct form extracts per byte into consecutive lanes:

  uint unpack_gguf(uint w, uint p) {
      const uint c4 = (w >> (8u*p)) & 0xFFu;
      return  (c4 & 3u) | (((c4>>2)&3u)<<8)
           | (((c4>>4)&3u)<<16) | (((c4>>6)&3u)<<24);
  }

and pairs code group p of word `widx` with activation word `4*widx + p`,
which is the same activation indexing the repacked path uses.

THE REPACK BUYS NOTHING ON VULKAN
---------------------------------
Reproducible across three runs, GGUF-order is 2-8% FASTER than the
repacked layout despite doing more ALU work per code (four shift/mask/or
chains instead of one mask). Both stream identical bytes.

This is the opposite of CUDA, where the repack (v3) gained ~1% over the
GGUF-order gather (v2). The practical consequence is the useful one:
**the ggml-vulkan integration needs no repack, no new weight layout, and
no on-disk format change** -- only the extraction function above plus the
type added to the MMVQ gates. That removes the main objection to doing
it.
