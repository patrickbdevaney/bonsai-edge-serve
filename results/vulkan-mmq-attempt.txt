===================================================================================

THE GATE CHAIN, WHICH IS THE ACTUAL FINDING
--------------------------------------------
Getting a type onto the Vulkan integer-dot MMQ path requires SEVEN separate
opt-ins, and every one of them fails CLOSED and SILENTLY:

  1. glslc implements GL_EXT_integer_dot_product
  2. type in the MMQ generate list          (vulkan-shaders-gen.cpp ~594)
  3. QUANT_R_MMQ + block_a_cache            (mul_mmq_shmem_types.glsl)
  4. the three shader functions             (mul_mmq_funcs.glsl)
  5. block_a_size in the shmem-support switch, whose `default:` is
     `return false` -- which clears device->mul_mat_{s,m,l}_int[t]
  6. CREATE_MMQ registration, itself guarded by those same flags
  7. something still unidentified

Miss any one and the result is identical: `ggml_vk_get_mul_mat_mat_pipeline`
returns nullptr for Q8_1, the caller sets `quantize_y = false`, and the
dequant matmul runs. No error, no warning, correct output, unchanged speed.

That is the same shape as the MMVQ integration (WIKI L8), where a missing
entry in one allow-list cost a 34% win and looked exactly like "the kernel
is no faster". The lesson generalises: **in this subsystem, "no speedup" is
the default failure mode, so a null result is not evidence that a kernel is
slow -- it is first evidence that the kernel did not run.** The cheap check
is the perf logger: if `quantize_q8_1` does not appear, nothing downstream
of it matters.

WHERE TO LOOK NEXT
------------------
`quantize_y` at ggml-vulkan.cpp:8257 is set before the pipeline lookup and
depends only on `integer_dot_product`, contiguity and `(ne11*ne10) % 4`. All
hold here. So `ggml_vk_get_mul_mat_mat_pipeline(..., GGML_TYPE_Q8_1, ...)`
is returning nullptr via `pipelines->is_empty()` at :6824, meaning none of
the s/m/l variants were created. Instrument
`ggml_vk_matmul_int_shmem_support` for these two types and print
`device->mul_mat_{s,m,l}_int[GGML_TYPE_Q2_0]` after initialisation -- that
distinguishes "flags cleared" from "CREATE_MMQ skipped for another reason"
in one run, and it is the check that should have been done before writing
any shader code.

IS IT WORTH FINISHING?
----------------------
Uncertain, and worth saying so. Thor has KHR_coopmat, so prefill already
runs on tensor cores via the dequant path at 345 tok/s. The MMQ shaders
here are the NON-coopmat scalar integer-dot variants (the generate gate is
`!coopmat && !coopmat2`). On a device with matrix cores it is entirely
possible that dequant+coopmat beats scalar int-dot MMQ, in which case the
correct outcome is that this path stays off and the work is a negative
result. That should be measured with a forced dispatch before more effort
goes in.


================================================================================
RESOLUTION: gate 7 was the coopmat branch, and MMQ loses to it by 2-3x
================================================================================

GATE 7: THE SHADER LOADER HAS THREE MUTUALLY EXCLUSIVE BRANCHES
----------------------------------------------------------------
`ggml_vk_load_shaders` is structured as:

  4017:  if (device->coopmat2)          { ... }
  4099:  if (device->coopmat_support)   { ... }   <-- Thor lands HERE (KHR_coopmat)
  4224:  if (device->fp16)              { ... }   <-- every CREATE_MMQ lives here
  4430:  } else { ... }

All MMQ registration -- for every quant type, not just ours -- sits in the
`fp16` branch, which is only reached when the device has NO cooperative-matrix
support. Thor has KHR_coopmat, so it takes the 4099 branch and creates no MMQ
pipeline of any type. `pipeline_dequant_mul_mat_mat_q8_1[Q2_0]` stays empty,
the mat-mat lookup returns nullptr, `quantize_y` is set false, and prefill
runs dequant+coopmat.

Nothing about q2_0/q1_0 was wrong. The pipelines were registered in a branch
this device never enters.

HOW IT WAS FOUND, AND THE MISSTEP ON THE WAY
----------------------------------------------
The plan recorded last time was right: print the flags and the pipeline
pointers after init. Doing it produced NO OUTPUT AT ALL -- not even the
`#else` arm that reports the feature macro being undefined.

The first reading was "the debug code didn't get built". It had: the string
was present in libggml-vulkan.so, twice, which also proved the `#else` arm was
compiled out and therefore that GGML_VULKAN_INTEGER_DOT_GLSLC_SUPPORT *was*
defined. Compiled, present, never executed -- which localises the problem to
an enclosing conditional and points straight at the branch structure.

(One real mistake first: `cmake --build --target llama-bench` does not rebuild
libggml-vulkan.so, so the first instrumented run used the old backend. The
timestamp on the .so, not the build log, is what settles that.)

A print that produces nothing is a measurement. It said "this code is
unreachable", which is a stronger statement than any value it could have
printed.

THE MEASUREMENT THAT CLOSES IT
-------------------------------
`GGML_VK_FORCE_MMQ_COOPMAT=1` registers the q2_0/q1_0 MMQ pipelines inside the
coopmat branch, so both paths can be compared on the same device and binary.

  model         dequant + coopmat    forced scalar int-dot MMQ    ratio
  ternary Q2_0      338.78 pp512            121.70 pp512          0.36x
  1-bit   Q1_0      320.97 pp512            142.94 pp512          0.45x

Scalar integer-dot MMQ is 2.2-2.8x SLOWER. That is the expected direction and
the reason upstream gates MMQ to non-coopmat devices: the dequant path feeds
Thor's tensor cores through KHR_coopmat, while these shaders are scalar
`dotPacked4x8AccSat` and cannot use them at all. Prefill is compute-bound, so
losing the matrix cores costs far more than saving the dequantisation.

Decode is unaffected either way (16.55 / 20.18 tok/s), because decode uses
MMVQ, which is a different path and remains the shipped W26 win.

WHAT THIS MEANS FOR THE WORK
-----------------------------
The MMQ shaders, the shmem accounting, the block_a_cache layouts and the
registration are correct and stay in the tree. They are simply for a device
class this one is not: a Vulkan GPU with integer dot product but WITHOUT
cooperative matrix. On such a device this is the right path and it is ready.

On Thor the correct configuration is the one that was already running by
default. The measurable outcome of this whole thread is therefore:

  * the MMVQ decode win (W26), which shipped and stands
  * a documented reason NOT to pursue MMQ prefill here
  * `GGML_VK_FORCE_MMQ_COOPMAT=1`, which makes the comparison repeatable

THE GENERALISABLE PART
-----------------------
Seven gates, every one failing closed and silently, and the seventh was not a
gate on our type at all -- it was which of three mutually exclusive branches
the device takes. Six type-specific checks were verified before the structural
question ("is this code even reached on this device?") was asked, and that
question was cheaper than all six.

Ask what the device selects before verifying what the feature requires.
