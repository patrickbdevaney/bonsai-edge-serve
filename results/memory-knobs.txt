Memory knobs for 1-bit + DSpark on Jetson Thor
==============================================

Two knobs were proposed to fit 1-bit 27B + DSpark into 8 GB:
  A. BONSAI_DSPARK_MAX_BATCH -- cap the drafter's staging batch
     (patches/0001-dspark-staging-batch-cap.patch)
  B. BONSAI_FORCE_RS_SEQ0    -- force the target's recurrent-state
     rollback ring to zero, falling back to host-side state checkpoints
     (patches/0002-force-rs-seq0.patch)

Measured, onebit dspark, CUDA, code workload, 128 tokens:

  ctx    cap    rs0   total MiB   code tok/s
  4096   none    0      8355        32.71     <- reference behaviour
  4096   256     0      7320        32.74     <- knob A only
  4096   256     1      5996        13.55     <- A + B
  2048   256     1      5838        13.50     <- A + B, short ctx
  2048   256     0      7162        32.95     <- knob A only, short ctx

VERDICT
-------
Knob A is free: -1035 MiB at ctx 4096 with throughput unchanged
(32.71 -> 32.74) and zero speculation fallbacks. Keep it.

Knob B is NOT free and is in fact strictly dominated. It saves a further
1324 MiB -- exactly the predicted ~1.3 GB -- but costs 59% of throughput
(32.74 -> 13.55) AND drops acceptance from 61.6% to 41.8%.

The comparison that settles it is against simply not speculating:

  1-bit native,      ctx 4096:  4173 MiB   18.61 tok/s
  1-bit dspark A+B,  ctx 4096:  5996 MiB   13.55 tok/s

Native is SMALLER AND FASTER. So there is no memory budget at which
knob B is the right choice: any budget that cannot afford knob-A-only
DSpark is better served by turning speculation off entirely.

WHY ACCEPTANCE DROPS -- the part that is not about memcpy cost
--------------------------------------------------------------
The expectation was that n_rs_seq=0 trades device memory for a host
state memcpy, which on unified memory is DRAM-to-DRAM and therefore
cheap. That is not what happens.

With n_rs_seq=0, `use_ckpt_tgt` is true for every partial acceptance
(server-context.cpp: `n_rollback > llama_n_rs_seq(ctx_tgt)`). That branch
does three things beyond the memcpy:

  slot.spec_draft = std::move(accepted);      // truncate the draft
  ckpt.load_tgt(...);                         // restore target state
  slot.prompt.tokens.keep_first(ckpt.n_tokens);
  continue;                                   // <-- skips accept()

The `continue` bypasses
`common_speculative_accept(spec.get(), slot.id, accepted.size() - 1)`,
so the DRAFTER is never told what the target accepted, and the rollback
goes to the checkpoint position rather than to the accepted position --
discarding accepted tokens as well as rejected ones.

So the cost is structural, not bandwidth: the round's work is partly
thrown away and the drafter's bookkeeping never advances, which is why
acceptance falls 61.6% -> 41.8%. A cheaper host memcpy would not fix it.

CONSEQUENCE FOR THE 8 GB TARGET
-------------------------------
The realistic options on an 8 GB Orin Nano Super, in order:

  1-bit native, ctx 4096          4173 MiB   18.61 tok/s   comfortable
  1-bit native + n-gram, ctx 4096 4173 MiB   ~18.6 tok/s   grounded work only
  1-bit dspark + knob A, ctx 2048 7162 MiB   32.95 tok/s   tight, OS must fit too

Knob B does not appear, because it is dominated everywhere.
