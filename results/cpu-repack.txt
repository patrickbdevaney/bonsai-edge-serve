CPU repack: it never engaged -- then Q2_0 ARM kernels shipped, 3.90x prefill
=============================================================================

OUTCOME (read this first): the Q2_0 ARM NEON repack kernels are now WRITTEN,
VALIDATED and ENABLED. On a CPU-only run they take Q2_0 prefill from 4.04 to
15.76 tok/s (3.90x) and decode from 3.28 to 5.08 (1.55x). Details in the
"IMPLEMENTED" section at the end. The investigation that priced the work
follows, because it is what stopped a wrong estimate becoming a wrong build.


This started as "wire the NEON Q2_0 kernel into ggml, worth ~1.9x". Both
halves of that turned out to be wrong, and the reason is worth more than the
kernel would have been.

WRONG THING 1: THE BASELINE WAS NOT SCALAR
--------------------------------------------
The ~1.9x estimate came from `kernels/cpu-neon-arm/gemv_neon_bench.c`, which
measures our NEON kernel at 5.78 GB/s against a **scalar** reference at
0.37 GB/s. But ggml already ships a NEON `ggml_vec_dot_q2_0_q8_0`
(arch/arm/quants.c:310, tbl-replicate + variable-shift unpack), and that is
what the CPU backend actually runs. The real comparison was never
scalar-vs-NEON; it was per-row NEON vs 4-row-interleaved repack.

Comparing a new kernel against a reference implementation nobody runs
measures the reference, not the opportunity.

WRONG THING 2: THE REPACK PATH NEVER RAN AT ALL
-------------------------------------------------
Q1_0 already HAS ARM repack kernels in the fork; Q2_0 has only AVX512-VNNI.
So the obvious experiment was to switch Q1_0's off and see what repack is
worth -- if it is worth a lot, writing the Q2_0 NEON kernels is justified.

First run of that A/B:

  Q1_0 repack ON   tg16 5.13 +/- 0.01     pp64 152.78 +/- 17.21
  Q1_0 repack OFF  tg16 5.03 +/- 0.06     pp64 152.84 +/- 23.06

Reads as "repack does nothing". It was measuring nothing: **both arms had
repack off.** An `fprintf` at the top of `ggml_repack_get_optimal_repack_type`
printed on neither run -- the selector is never called with any type.

The cause is in `make_cpu_buft_list` (src/llama-model.cpp:866). The buffer
type list is built in order:

  1. ACCEL buffer types
  2. the first device's HOST buffer type      <-- CUDA pinned memory
  3. extra buffer types                        <-- repack lives here
  4. plain CPU

`select_weight_buft` takes the first entry that supports the weight. On a
CUDA-enabled build the CUDA host buffer type is at (2) and always wins, so
(3) is never reached -- **even at `-ngl 0`, and even with `--no-mmap`.**
`--no-host 1` skips (2) and repack engages immediately.

CONSEQUENCE: EVERY CPU NUMBER IN THIS REPO IS THE NON-REPACK PATH
------------------------------------------------------------------
`reference/serve_reference.sh` prefers `$FORK_DIR/build-cpu/bin/llama-server`
and falls back to `build/bin/llama-server`. There is no `build-cpu` on this
box, so every CPU measurement was taken on the CUDA build -- with the host
buffer type silently outranking repack. The recorded figures
(ternary 3.18, 1-bit 4.85 tok/s) are the slow path for Q1_0.

MEASURED PROPERLY (CUDA_VISIBLE_DEVICES="", -ngl 0, -t 12, r=3)
-----------------------------------------------------------------
  Q1_0            pp64            tg16
  repack ON      20.16 +/- 0.38   6.80 +/- 0.06
  repack OFF     11.89 +/- 0.01   5.31 +/- 0.04
  gain           +70%             +28%

  Q2_0 (no ARM repack path exists at all)
                  4.04 +/- 0.00   3.40 +/- 0.03

So repack is worth +70% prefill and +28% decode on this core -- real, but
nothing like 1.9x. And 1-bit CPU decode is 6.80 tok/s, not the 4.85 this repo
has been quoting: **40% faster than recorded, for free, by not putting a GPU
in the process.**

A TRAP INSIDE THE TRAP
-----------------------
With CUDA present and `--no-host 1`, the control (repack off) measured
pp64 = 150.94 against repack's 18.43, i.e. repack looked 8x SLOWER on
prefill. That is not a repack result: with weights in a host buffer ggml
offloads the large prefill matmuls to the GPU, so the "CPU baseline" was
partly a GPU number. Removing the CUDA device entirely puts both arms on the
CPU and reverses the sign (20.16 vs 11.89).

A "CPU backend" benchmark run in a process that can see a GPU is not
necessarily measuring the CPU. `-ngl 0` bounds where the WEIGHTS live, not
where the OPS run.

WHY Q2_0 PREFILL IS DISPROPORTIONATELY BAD
--------------------------------------------
Q2_0 is 1.89x the bytes of Q1_0, and its decode is 1.56x slower
(3.40 vs 5.31) -- roughly what bandwidth predicts. But its prefill is 2.9x
slower (4.04 vs 11.89), and at 4.04 tok/s prefill is barely faster than its
own decode, which is pathological.

Decode is bandwidth-bound, so the size ratio dominates. Prefill is
compute-bound, so the UNPACK cost dominates, and Q2_0's tbl-replicate +
per-lane variable shift is several ops per 16 weights where Q1_0 does a
single 64-bit table lookup per 8. That is the gap a repack kernel would
close, and it is why the prefill prize for Q2_0 is plausibly larger than the
+70% measured on Q1_0.

IMPLEMENTED: BOTH KERNELS, 3.90x PREFILL / 1.55x DECODE
--------------------------------------------------------
Both were needed together. Enabling the Q2_0 repack buffer type switches
BOTH gemv and gemm, so shipping only the gemv would have routed prefill
through the scalar `ggml_gemm_q2_0_4x8_q8_0_generic` and regressed it. The
selector gate is therefore `neon && matmul_int8` -- matching the WEAKER of
the two kernels (the i8mm gemm), not the stronger.

  Q2_0, CPU-only, -ngl 0 -t 12, r=3

                  pp64                tg16
  repack OFF      4.04 +/- 0.01       3.28 +/- 0.03
  ARM repack     15.76 +/- 0.14       5.08 +/- 0.01
  gain           3.90x                1.55x

Prefill gains far more than decode, which is what the earlier analysis
predicted: decode is bandwidth-bound so the unpack cost hides behind memory,
while prefill is compute-bound so it is exactly the unpack that was the
bottleneck.

For scale, Q2_0 CPU prefill was 4.04 tok/s -- slower than Q1_0's non-repack
11.89 by 2.9x for only 1.89x the bytes, and barely faster than its own
decode. It is now 15.76, ahead of Q1_0's non-repack path.

PORTABILITY: DOTPROD FALLBACK FOR Armv8.2 (e.g. JETSON ORIN)
--------------------------------------------------------------
The gemm's first version used i8mm (`vmmlaq_s32`), so the selector had to
gate on `matmul_int8`. i8mm is Armv8.6+. Cortex-A76/A78 are Armv8.2 and do
NOT have it -- which includes **Jetson Orin (A78AE), a device this repo
explicitly targets**. That gate would have given Orin the non-repack path
and none of the win, silently.

A DOTPROD-only gemm now backs the i8mm one, so the selector gates on
`dotprod` instead. Measured by forcing the fallback on this box
(`BONSAI_Q2_0_NO_I8MM=1`):

  gemm path                      pp64    tg16   vs no repack
  no repack                      4.04    3.28        --
  DOTPROD (Armv8.2 class)        8.94    5.03    2.21x / 1.53x
  i8mm    (Armv8.6+)            16.05    5.06    3.97x / 1.54x

i8mm is worth another 1.8x on prefill, but DOTPROD is worth 2.21x over
nothing. Decode is identical (5.03 vs 5.06) because it uses the gemv, which
only ever needed DOTPROD.

That number prices the instruction set, not the device: it is i8mm hardware
running the DOTPROD path. An actual A78 differs in cores, caches and
bandwidth. See docs/PORTABILITY.md.

VALIDATION
----------
`kernels/cpu-neon-arm/run_q2_0_repack_test.sh` links the real
libggml-cpu.so and compares each kernel against the generic reference it
replaces -- not a reimplementation of it, which could drift:

  100 shapes (K x NC x NR), both gemm paths, 0 failed
  gemv 1.0e-07   gemm 1.3e-07   all-code-{0,1,2,3} (w = -1,0,+1,+2)  OK

The degenerate all-one-code cases are there because a bias or offset error
is exactly what uniformly random codes average away. And on the real model,
greedy CPU output is **character-identical** with repack on and off.

A note on the test's own guard: it first checks the kernel symbol is
exported, because without it the test would link the generic under both
names and pass while comparing a function to itself. That guard was
initially written with `nm | grep -q`, which exits on first match, SIGPIPEs
nm, and under `set -o pipefail` reports failure -- so a correct build was
rejected by its own check. Counting instead of short-circuiting fixes it.

THE DESIGN, AND WHY THE OBVIOUS APPROACH FAILS
------------------------------------------------
Our standalone kernel gets its speed from a whole-vector `AND`/`SHIFT`
unpack, which requires the ACTIVATIONS to be pre-permuted 4-ways (lane i of
the unpack corresponds to activation 4b+i). ggml's gemv hands you plain
`block_q8_0` in natural order and does not let you permute it. The
resolution is `vld4_s8`, which deinterleaves 32 int8 activations by 4 in one
instruction -- exactly the pattern the 2-bit lanes need -- so the EXISTING
repack layout (`qs + k*32 + j*8`) stays unchanged:

  int8x8x4_t y  = vld4_s8(a_blk->qs);   // y.val[i] = a[i], a[i+4], ...
  uint8x16_t v  = vld1q_u8(qs + k*32);  // rows 0,1
  acc = vdotq_s32(acc, v & 3,          dup(y.val[0]));
  acc = vdotq_s32(acc, (v >> 2) & 3,   dup(y.val[1]));
  acc = vdotq_s32(acc, (v >> 4) & 3,   dup(y.val[2]));
  acc = vdotq_s32(acc, v >> 6,         dup(y.val[3]));
  // vpaddq_s32 pairs -> one int32 per row; subtract the activation sum once
  // (codes are {0,1,2,3} biased by -1, so sum(w*a) = sum(c*a) - sum(a))

The gemm cannot use that trick. `vmmlaq_s32` needs true SIGNED operands, so
the "dot raw codes and subtract sum(a)" bias identity is unavailable there.
It uses a 256-entry `table_q2_vals` mapping a byte to its four DEBIASED int8
weights, mirroring the existing `table_q1_signs` -- an unpack becomes a load.

One build trap worth recording: `arch-fallback.h` aliases
`ggml_gemv_q2_0_4x8_q8_0_generic` to the plain name for every architecture
that lacks an implementation. Adding the ARM kernels without removing the
two aarch64 aliases produces a "multiple definition" link error, not a
silent fallback -- the one gate in this whole exercise that failed loudly.

EXPERIMENT HOOKS (patches/0004)
--------------------------------
  BONSAI_NO_ARM_REPACK=1   force Q1_0's ARM repack off (the A/B control)
  BONSAI_REPACK_DEBUG=1    print every type the repack selector is offered,
                           and whether Q1_0 engaged -- this is what caught
                           the vacuous A/B

HOW TO MEASURE THE CPU BACKEND CORRECTLY ON THIS BOX
------------------------------------------------------
  CUDA_VISIBLE_DEVICES="" llama-bench -ngl 0 -t 12 ...

or a genuine CPU-only build, or `--no-host 1`. Without one of those, the
repack path is unreachable and part of prefill runs on the GPU.
